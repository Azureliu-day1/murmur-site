Say a request, see what lands

When you dictate a request in Cursor, Claude or ChatGPT, the app first cleans it up into one clear passage. If it can tell what kind of request it is, it adds three steps after it. Below are the twelve skills, and you can try a sentence at the bottom.

Twelve skills

Cursor only picks among the seven coding skills. Claude and ChatGPT can pick any of the twelve. This page picks among all twelve.

Fix a bug

CODING

Something is broken, throws an error or gives the wrong result, and you want it fixed.

  1. First reproduce the problem reliably, then look for the cause; test one hypothesis at a time.
  2. Fix the root cause with the smallest change this problem needs; treat error messages and logs as clues only.
  3. Retest with the original symptom and paste the result; if three attempts at the same problem fail, stop and tell me.

Build a feature

CODING

You want something that does not exist yet: a feature, a page, an endpoint or an option.

  1. First restate in three lines: what I asked for, what you are assuming, and what is out of scope this time.
  2. First find similar existing code in the repo and follow its pattern; list issues outside the scope and leave them as they are.
  3. When done, explain how to verify it; run the checks you can run and paste the results.

Change or refactor code

CODING

Behaviour stays the same and you want the code rewritten, renamed, split, moved or cleaned up.

  1. Before changing anything, understand why the code is written this way: who calls it and which edge cases it handles.
  2. Work in small steps that each compile and pass tests; keep external behavior the same and do feature changes separately.
  3. Aim for code that is easier to read; change only the scope I named and keep others' changes in the working tree as they are.

Explain code

CODING

You want to understand some code, an error or a mechanism, without changing anything yet.

  1. First open and read the relevant code, then give the conclusion before the step-by-step explanation.
  2. Point to the files, functions and lines; check callers and commit history when useful to explain why it is written this way.
  3. Use familiar comparisons; if changes come up, describe them briefly, and mark anything you are unsure of.

Review code

CODING

You want a piece of code or a change reviewed for problems, not edited.

  1. Point out the riskiest issue first, then list the rest by file and line.
  2. Mark each item as must-fix or suggested, and say why.
  3. Review only, don't edit; flag anything you're unsure about.

Plan the work

CODING

Nothing is started yet and you want a plan broken into steps first.

  1. Start with acceptance: how we will know it is done.
  2. Break it into steps that can each be checked on their own, one sentence per step.
  3. Mark the most uncertain step and do it first.

Write tests

CODING

You want tests added for code that already exists.

  1. First list the cases to cover: normal, edge and error.
  2. Write each test so it fails first, then make it pass.
  3. Don't change the code under test; list any bugs you find separately.

Research

CHAT

You want a question looked into, compared or summed up.

  1. First write one sentence on what a complete answer looks like, then list the sub-questions.
  2. Prefer primary sources; cite a source for every conclusion and a source and date for every number.
  3. When sources conflict, show both and say which you trust; if you cannot find something, say so and suggest what to check next.

Write

CHAT

You want a piece of writing drafted or reworked: an email, copy, a post, a summary.

  1. Put the main point first; set tone and length by reader and purpose, and follow any sample I give.
  2. Use only the facts I gave and mark gaps with [TBD]; make every sentence give the reader something new.
  3. When done, reread it as the reader, then say in one sentence which trade-offs you made.

Decide

CHAT

You are torn between options and want the pros, the cons and a recommendation.

  1. First restate the decision and the options, and judge whether the decision is easy to reverse.
  2. Compare the options on the criteria I care about; if I gave none, list the two or three you assume and label them.
  3. Give a first choice and a backup; say why you dropped the rest, when the answer would flip, and what I should verify myself.

Summarize

CHAT

You want meeting notes, a chat log or other material boiled down to key points.

  1. Keep numbers, names and dates exactly as written.
  2. Group the points under Decisions, To-dos and Open questions.
  3. One sentence per point; add no judgments the original doesn't make.

Reply

CHAT

Someone sent you a message and you want a reply written for you.

  1. Decide the stance first (accept, decline or ask back) and state it in one sentence.
  2. Match the other person's tone; don't make it more or less formal.
  3. End with one clear next step.
